# Done

- Duplicate-effect handling: selecting an effect already selected elsewhere no longer blocks the click — both instances render with a warning state instead. Button states: selected, duplicate warning, discouraged-but-clickable (occupied slot / taken elsewhere), filter-recommended.
- Client-side render/state architecture rewrite: catalog (category → item → slot → color → candidates) built once at load, separate from a selections store (positional + inherent), replacing the old flat-array/boundary-flag model. Save format bumped to v2.0 — **not backward-compatible** with older save files.
- Named/custom item feature: replaced the earlier plan to hand-curate a handful of named items with data. Instead, any category can be switched to "Custom," which provides:
  - Real augment slots (same color-eligibility rules as Cannith augments), added via a "+ Add Augment" control, capped at 7 per item, individually removable.
  - A flat, alphabetical inherent-effects picker covering every known effect, deliberately unfiltered by category and with no level gating.
  - A per-category overlap warning banner for a custom item's own selections, instead of the individual per-button duplicate highlight Cannith picks get.
  - Switching a category's mode never deletes its data — toggling back and forth preserves whatever was entered.
- Removed the old Cannith item-choice dropdown from category headers (dead code since the custom-item pivot — there was never more than one real option).
- Data pipeline: `source_data/equipDDO.sqlite` is the source of truth; `ddocraft.json` is generated from it via `build_db.py` → `apply_corrections.py` → `export_ddocraft_json.py`. **Never hand-edit `ddocraft.json` directly** — edit the SQLite data and regenerate.
- Corrected several bonus-type data-entry errors in the recovered source data: effect-name leakage into the bonus-type column (Blindness Immunity, Regeneration, the material-bypass family, plus two rows already using a literal "Unknown" placeholder — all normalized to "Untyped"), and a `Competance`/`Competancy` spelling split merged to `Competence`. Vitality was checked and confirmed to be a real, distinct bonus type — left as-is.
- Stood up a MariaDB backend on a dedicated dev/QA VM. Populated: `bonusType`, `augmentColor` (reference tables), `effect` (283 rows, via `db/populate_effect.py`), `effectBonusByLevel` (7,359 rows, via `db/populate_effect_bonus.py`), `itemCategory` (18 rows, via `db/populate_item_category.py`), `augmentOption` (104 rows) and `cannithCategoryOption` (1,307 rows) (both via `db/populate_category_options.py`). All migrated from the recovered `equipDDO.sqlite` data; each script's docstring documents the mapping logic.
- The one-off "Tourney Armor" stand-in item used during early named-item design has been fully removed from the data pipeline — it was never itself important, just an example.
- Built and deployed a real API server (`server/`, Express + TypeScript + `mysql2`, using the `ddocraft_web` account): `/api/health`, `/api/bonus-types`, `/api/augment-colors`, `/api/effects`, `/api/effects/:id/bonus`. Running on the dev VM on port 3001, verified against live data. Not yet wired to the client, and doesn't yet have endpoints for `itemCategory`/`augmentOption`/`cannithCategoryOption` (see To Do).
- Added table-prefixed sort-order columns, following the recovered data's `<table>SortOrder` convention: `effect.sortOrder` → `effectSortOrder`; new `itemCategorySortOrder`, `augmentOptionSortOrder`, `cannithCategoryOptionSortOrder`. The recovered `itemOptionSortOrder` turned out to be a coarse constant for the category/augment-option data (not a real per-row order) - the real curated order was recovered from `itemOptionID`'s insertion sequence instead.
- Deployed the (still old, static-`ddocraft.json`-based) client to the dev VM as its own nginx site, separate from the existing codehawkins.com config - port 8080, plain HTTP, PHP 7.4-FPM passthrough, served from `/home/claude/ddocraft`. Config at `/etc/nginx/sites-available/ddocraft`. - Round of fixes from browser-testing the deployed dev site (2026-07-28):
  - Renamed the named-item-only "Damage Reduction (Adamantine)" effect to just "Damage Reduction" - Adamantine is the delivery mechanism, not part of the effect's identity.
  - Added weapon material-bypass effects Flametouched Iron and Crystal (Red-augment options, same family as Adamantine (Weapon)/Byeshk/Cold Iron/Silver), and Transmuting (bypasses any/all DR - material, alignment, or otherwise; Cannith-only on weapon Suffix, same treatment as the universal "Aligned" effect). Min levels are placeholder/TBD (see Known Issues).
  - Reversed the "questionable" exclusion on the 6 Insightful Ability effects - confirmed via the original hand-curated flat file that this wasn't data loss (Belt already offered Insightful Ability (Constitution)/(Strength) in the pre-migration data too), just an over-cautious Phase 1 exclusion.
  - `enchSupercededBy` (the "this effect is superseded by a better one" mechanism) is now checked globally instead of only within the same item, since the superior/inferior pair are often on different items entirely (e.g. True Sight on Goggles superseding Blindness Immunity elsewhere). Added the Blindness Immunity → True Sight link as the first real cross-item example, alongside the pre-existing Chaos/Evil/Good/Law Aligned → Aligned links.
  - Named/custom items: added a collapse toggle to augment-slot color sub-headers (Cannith slots already had one), and a freeform Description field.
  - Renamed the "Named or Custom Item" checkbox label to "Named/Custom"; moved the "+ Add Augment" control from the category header into the item's Name row (separated from the name field); removed the "e.g. Tourney Armor" placeholder text; the result table now shows "`<Item Name>` (Category)" for custom items instead of the raw `custom:Category` key.
- Collapse redesigned into a universal pruning behavior, everywhere (Cannith and named/custom alike), replacing both the old simple show/hide collapse AND the short-lived "Mark Done" toggle (superseded before shipping - same goal, one mechanism instead of two): collapsing any container - category, slot, or augment color - keeps only what's actually selected inside it and hides the rest; a container with nothing selected at all still keeps its own header visible as a button to re-expand, but empty descendants nested inside a collapsed ancestor vanish completely rather than showing as empty placeholders. Also fixes a real bug: named-item augment slots stopped collapsing at all once the augment "remove" (×) button was added, because the click handler had silently shrunk to just the label text instead of the whole header cell.
- Empty slots (Cannith, named/custom augment slots, and Inherent Effects) no longer vanish when collapsed - they show what's still available instead: "Unused. N options available." (counting only options that pass the level gate and active filter, exactly matching what expanding the slot would show), or "Unused. No options currently available." Inherent Effects uses its own wording, "No effects identified.", with no count - those aren't really options to choose so much as properties to identify.
- Named/custom augment slot labels dropped their color parenthetical - "Augment 1 (Blue)" is back to plain "Augment 1", matching Cannith - the color already shows via the color sub-header in column 2, and repeating it made collapsed rows taller than necessary.
- Collapse state redesigned to be fully hierarchical and independently tracked at every level, replacing the old inherited-at-render-time "pruneMode" model: collapsing (or expanding) a category now really does collapse/expand every one of its slots and their colors, immediately, in the data - not just visually. So a category you collapsed can have any individual slot re-expanded on its own, and the category itself now stays correctly marked as collapsed only for as long as every one of its slots agrees. The reverse works the same way one level down: manually collapsing (or expanding) every color in a slot marks that whole slot collapsed/expanded too, which can in turn mark the category. Deliberately not done: expanding a single slot does not mark its category expanded - only full agreement across every slot moves the category's own flag.
