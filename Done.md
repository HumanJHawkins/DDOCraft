- Phase 1 of DB-backed character saves: added a `characterBuild` table (`db/ddocraft_schema.sql`) and a full CRUD API (`server/src/routes/characterBuilds.ts`, mounted at `/api/character-builds`) - create, list (light-weight, no build payload), fetch one (full payload), update, delete. - Added a temporary test harness (`ddocraft.php`/`ddocraft.js`) so the DB-backed save/open API can be exercised from the actual browser, not just curl - a "Test User ID" field plus Save to Server / Open from Server buttons, explicitly throwaway (replaced wholesale once real accounts exist). - `characterBuild.characterBuildId` is now an app-generated random GUID (v4) instead of a sequential auto-increment integer, replacing the id entirely rather than adding a second identifier alongside it. This is what makes "open a build" a safe link to hand to someone else: a random 122-bit value can't be guessed or enumerated the way a small sequential integer could, so there's no need for a separate "share" mechanism, permission toggle, or token table - opening your own build and opening a build someone sent you are the same GET request, and knowing the id is itself sufficient (same principle as a "anyone with the link" Google Docs URL). The single-build GET route dropped its `userId` requirement accordingly; list/update/delete still require the owning `userId`.
- Added `buildChecksum`: a SHA-256 hash over a canonicalized subset of a build - `charLevel` plus every item/category field (selections, categoryMode, custom item names/descriptions/augment colors) - deliberately excluding ownership/history (id, userId, charName, description, dates) and UI-only state (collapsed, and the arbitrary per-augment-slot add-order id). Canonicalization sorts everything first, so the same set of choices hashes identically regardless of what order they were made in - verified directly: two builds built in reverse order, with different owners, names, and internal augment ids, produced the identical checksum, while changing `charLevel` alone changed it. Lets two saves be recognized as mechanically the same build regardless of who made them or what they're called - e.g. surfacing builds independently arrived at by multiple users (see TO DO.md's "popular named/custom items" idea, which this now directly feeds) or catching a redundant re-save.
- `buildChecksum` is now actually used: saving to the server checks for an existing row with the same `userId` + `charName` + `buildChecksum` first. A match updates that row in place (still persisting `description`/`appVersion` in case either changed even though the build/name didn't) and reports `created:false` with the existing id, instead of piling up duplicate rows every time someone re-saves without meaningful changes. `charName` deliberately isn't folded into the stored checksum itself (which stays name-agnostic, for the cross-user matching use case above) - it's composed as a separate condition on this one query instead, since a mechanically-identical build saved under a different name is a deliberate second save, not a duplicate of the first.
- Replaced the prompt()-based build picker with a real "Open Build" modal (same show/hide pattern as Preferences/Help/About): a sortable table (Name/Level/Updated, click a header to sort/reverse) with formatted local datetimes. Each row's Open control is a real `<a href="ddocraft.php?openBuild=<guid>">` rather than a JS-only button, specifically so the browser's native right-click "open in new tab," middle-click, and ctrl-click all work unmodified - a plain click is the only case intercepted, for a fast in-page load. A new `loadCharacterBuildFromUrl()` check on page load means a direct navigation to that URL (new tab, bookmark, pasted link) loads the build on its own, the same as going through the dialog.

- Collapse state redesigned to be fully hierarchical and independently tracked at every level, replacing the old inherited-at-render-time "pruneMode" model: collapsing (or expanding) a category now really does collapse/expand every one of its slots and their colors, immediately, in the data - not just visually. So a category you collapsed can have any individual slot re-expanded on its own, and the category itself now stays correctly marked as collapsed only for as long as every one of its slots agrees. The reverse works the same way one level down: manually collapsing (or expanding) every color in a slot marks that whole slot collapsed/expanded too, which can in turn mark the category. Deliberately not done: expanding a single slot does not mark its category expanded - only full agreement across every slot moves the category's own flag.
